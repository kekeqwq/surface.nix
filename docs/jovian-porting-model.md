# Porting Denali like Jovian-NixOS

## What Jovian actually ports

Reviewed Jovian-NixOS at `759dd31`. The [getting-started guide](https://github.com/Jovian-Experiments/Jovian-NixOS/blob/759dd31/docs/getting-started.md) treats installing NixOS and enabling Jovian as separate tasks. Its [flake](https://github.com/Jovian-Experiments/Jovian-NixOS/blob/759dd31/flake.nix) exports a module, overlay and checks, not a SteamOS conversion installer or an ISO. SteamOS is the downstream hardware reference, not the root filesystem of a Jovian installation.

The [Steam Deck module](https://github.com/Jovian-Experiments/Jovian-NixOS/blob/759dd31/modules/devices/steamdeck/default.nix) is opt-in and composes hardware-specific kernel, firmware, audio, input, power and other modules. Its [kernel derivation](https://github.com/Jovian-Experiments/Jovian-NixOS/blob/759dd31/pkgs/linux/default.nix) builds a pinned vendor-derived tree from source, translating relevant downstream configuration into `structuredExtraConfig`. Its modules select those kernel packages by default and separately add upstream/vendor firmware and targeted userspace integrations. Disk layout, machine identity, and other host choices belong to the host consuming the module.

## Apply the same boundary to Surface Pro 11

Treat the working Arch system as the Linux hardware reference, not as a distribution image to convert. Both the original Arch Live and an installed Arch system have now booted on this unit. The installed system is the ARM64 build host and a separate known-good disk-boot reference; neither Arch boot proves NixOS boot.

| Layer | Ownership |
|---|---|
| `surface.nix` packages/overlay | `surfacePackages` contains pinned `linux-sp11`, its `linuxPackagesFor` set, and WCN7850 board data. Older `linux-next` and Arch ISO experiments are separate. |
| `surface.nix` device module | Explicit opt-in for Denali OLED; defaults for its kernel, module loading and hardware firmware. Device-specific input/audio are separate additions after the minimum works. No host users, disk IDs, desktop, network credentials or auto-installation. |
| Isolated bring-up target | UEFI/ESP, systemd-boot, stubble/zboot or another validated handoff, and matching initrd. Keep existing failure cases as diagnostics, not module defaults. Boot medium and installed-disk paths must be tested separately. |
| Personal host | Root/ESP, boot entries, identity, accounts, and eventually the existing desktop integration. No hardware dependencies in shared desktop/server configuration. |

The [Arch recipe at `94d875e2dec4`](https://github.com/dwhinham/archlinux-repo/blob/94d875e2dec4cb45f4038d706313b4922a669326/linux-sp11/PKGBUILD) pins kernel source `46bb6beace94874a3ec602bfb83e6f87995bc5d0`. The Nix derivation uses that tree and its exact Arch Ports base Kconfig (SHA-256 `e2182ed73234ccf4393a1f677b59772c7ae99ba9ffb64a64c35036c997c4a46f`), with the same two SPI HID settings. ## Acceptance gates

1. Evaluate and build the kernel, firmware check and independent native NixOS closure on Arch. Compare generated artifacts to the installed reference. This is package verification only.
2. `live/uki.nix` uses native NixOS `boot.uki` and the same Type #2 handoff. The separately built `denali-live-iso[-local]` contains one UKI in `/EFI/Linux/` on an appended EFI partition. The pinned Nixpkgs systemd is `262`; it is not a bit-for-bit copy of Arch's `262.2-1-arch` loader/stub. The NixOS initrd and Live squashfs/overlay root likewise replace the installed Arch initrd and ext4 root. The final ISO contract checks the GPT and El Torito paths to the same ESP, UKI content and Live root. This is an isolated USB probe; do not replace Arch's EFI entry or root. Prior remastered/handoff ISO failures are recorded in [the boot reference](arch-boot-reference.md).
3. Require `UEFI → kernel → initrd → NixOS TTY → Wi-Fi → SSH` before calling the module hardware-validated or publishing an installer. Keep the installed Arch baseline and the original Arch Live artifact available for comparison.

### First Type #2 USB test

The locally keyed ISO (SHA-256 `ce7b76f8410e8201cccb272756508057f8f74c33e2192d1d78e56ed81de284c2`) was raw-written to SanDisk and matched on full readback. Installed Arch recognized the same stick's `NIXOS_DENALI_UKI` ISO9660 label and the `DENALI` ESP. On bare metal the build passed UEFI and entered NixOS systemd initrd. It mounted the tmpfs `/sysroot` and writable store, but did not show the ISO mount or switch-root. The first attempt reported a `/dev/tpm0` wait; retrying the same USB with `systemd.tpm2_wait=0` exposed the wait for `/dev/disk/by-label/NIXOS_DENALI_UKI` before black screen. VT switching did not recover the display. This establishes an initrd device/path wait, not whether USB enumeration, storage binding, or udev label creation failed. `arm-smmu 3da0000.iommu` probe `-110` was also printed; its relevance is undetermined. Back in installed Arch, the same SanDisk stick was recognized via `a800000.usb` → `xhci-hcd.0.auto` → USB bus 1, with `/dev/disk/by-label/NIXOS_DENALI_UKI` pointing to its ISO9660 partition. The failed NixOS initrd already contained the storage drivers, `blkid`, and `60-persistent-storage.rules`. A comparison with the installed Arch initrd found that the NixOS initrd lacked `tcsrcc-x1e80100`. The DTB connects the eUSB2 and USB3 PHYs to the `qcom,x1e80100-tcsr` clock provider, and Arch binds it at `1fc0000.clock-controller`. The next candidate adds that module to the initrd and carries forward the already-tested `systemd.tpm2_wait=0` setting. The kernel, DTB, and systemd-boot payload hashes stayed unchanged. With that candidate (ISO SHA-256 `3c5a6430e5da277452851dcb667f2bfe53ddd72d38c3f4ffc14716f1a6e53ac2`), the device reached the `nixos@surface-live` TTY and ran `nmtui`. Linux exposed both a wireless interface and a USB Ethernet interface, but `nmtui` did not list Wi-Fi networks during the first observation. TTY passed on that candidate; Wi-Fi association and SSH were not yet validated.

### Live acceptance passed

The next locally keyed ISO (SHA-256 `3d5ba2f76e7ef2b3191344f6f6631d67ef5a51db28348faa10ab6297efd667dd`) removed the override that disabled NetworkManager's D-Bus-controlled `wpa_supplicant`; the kernel, DTB, and loader stayed unchanged. On Denali OLED the system reached TTY, associated over Wi-Fi, and accepted an SSH public-key login as `nixos`. The SSH session confirmed `ID=nixos`, kernel `7.3.4-arch1-1-sp11`, ISO9660 mounted at `/iso`, and active `getty@tty1`, NetworkManager, wpa_supplicant and sshd. This validates the Live USB path on this unit, not a persistent NixOS installation or the public ISO.
