# Denali touch and power: no-reboot qualification (2026-11-28)

This records [TODO-#1 and TODO-#2](../TODO.md) build and runtime trials, not overall hardware acceptance. No live forced touch binding was used. See below for the Gen 17 touch failure and the separate battery and suspend trials.

## Touch module / ADSP client

Build on native AArch64 from the repository with its locked inputs:

```sh
nix build -L --no-link --print-out-paths --max-jobs 1 --cores 4 \
  .#denali-touch-candidate .#denali-touch-dtb-candidate .#denali-adsp-pld-candidate
```

These outputs use `denaliDailyBoot.kernelPackages`. The Live image does not select any of them. The installed host may explicitly opt into the touch module and DTB together; the ADSP client is still build-only. Source revisions and unpacked NAR hashes are in `flake.nix`. On the Surface, native `W=1` Kbuild/`modpost` also passed for both the running long-release ABI and the locked `7.4.0-rc4-surface-next-20261124` ABI. The upstream ADSP callback fixture printed `PLD_CALLBACKS_TEST_OK`; it models callback control flow, not delivery of messages to the firmware.

The live `spi0.0` is bound to `spi_hid_of` at `geniqup@ac0000/spi@a88000/touchscreen@0`. Its parent is `qcom,geni-spi-qspi`; the node specifies four RX/TX lanes, 40 MHz, IRQ 51, reset GPIO 48 and a `vdd-supply` phandle. The candidate advertises `microsoft,mshw0485`, requests an `interrupt` GPIO by name, and implements a paired `power`/`reset` GPIO path. The live node instead uses `microsoft,denali-touchscreen`, `interrupts-extended`, `reset-gpios` and `vdd-supply`. Do not treat a matching vermagic, replacing the compatible string alone, or a forced runtime bind as a functional port. The GPIO/regulator ownership and QSPI transaction behavior still need a coordinated, mutually exclusive DT and driver test, with stock `iptsd` available on the fallback boot.

The Denali build-only touch pair now preserves `VREG_TS` (which already owns GPIO64), adds the regulator consumer to `mshw0485_touch` with logically asserted active-low GPIO48 reset, and declares GPIO51 as an active-low IRQ GPIO without changing the existing falling-edge interrupt cell. No duplicate `power-gpios` is added. The candidate DTB build requires the existing QSPI controller, DMA protocol 4 / SE2, 40 MHz, and four TX/RX lanes. A sorted DTB decompile diff confirmed exactly two edits: `compatible` and `interrupt-gpios`. The module inherits the current GENI/GPI code; wire behavior with the candidate client is still unverified.

Native AArch64 `W=1`/modpost passed against `7.4.0-rc4-surface-next-20261124`. Original DTB SHA-256 `68fb0c72b6f17b06eb826d7f8a9b6073c30c5b5a31f826512adac1f88c667a94`; candidate DTB `ff632b655644ba924e212854012f5892a6a034bd1de9e2a8cca8d87661657edd`; early unsigned candidate `.ko` `f71f0b957a4052237fd82203548a16314969ffddaac88c4111519022d3534026`. The deployment package uses Kbuild `modules_install` to sign the module and install its certificate alongside the compressed `.ko`. The running long-release ABI was not used to load the candidate. Official tags checked on 2026-11-28: mainline `v7.4-rc4` (`a4d7daea71be…`) and `next-20261127` (`7922eb284658…`). Kept Next24: the existing Next27 audit found two FullIO root conflicts, and these candidates required no kernel recompile or source change.

The exported `nixosModules.denali-native-touch` provides `surface.devices.denali.touchscreen.native.enable` (off by default). The disabled variant retains the stock DTB, `iptsd` and module closure. The enabled variant is restricted to the locked daily kernel and OLED DTB name, replaces the DTB, adds only the candidate module to the closure and disables `iptsd`. Binding is via the new DT's OF modalias after reboot, not a live unbind or modules-load action. ### Gen 17 failure and Next24 transport follow-up

Gen 17 (`flakes` `ac28707`) booted the short-release kernel and native-touch DTB. `mshw0485-touch` bound to `spi0.0`, IRQ 51 fired, and the input device appeared, but three attempts stopped at `reset-response` (`-EAGAIN`). Counters were 3 SPI messages/3 transfers, 24 TX bytes, 0 RX bytes and 0 contact frames; the owner confirmed no touch. This is a failed touch trial, not an IRQ, modalias, or compositor diagnosis. Surface evidence: `/tmp/denali-native-touch-gen17-failure.log`. The stock config switched successfully on disk (`41e7320`), but no reboot into that rollback was performed.

The pinned `production-v1` client builds two transfers (TX command then RX data) for unified13's custom pairing path. The fully patched Next24 GENI controller has no such message hook. Its working stock SPI-HID client uses one transfer with both buffers; GENI recognizes `0xeb` and configures `SPI_TX_RX`, four command bytes and controller-generated dummy clocks. `denali-mshw0485-next24-transport.patch` makes only the optional client follow that contract, with heap-backed TX/RX buffers for DMA and bounded copies. The kernel, DTB, reset/power sequence, stock touch, Live, and suspend configuration are unchanged. Native AArch64 `W=1` build, signing/aggregation, native/stock evaluation and Live checks passed. The transport correction still needs a boot, valid reset/header/Heat frames and physical input acceptance.

For the power series from `geocausa/sp11-suspend-resume-public@0376e25`, `git apply --check` against exact Next24 sources rejected the QCE, WSA, PAS/SMP2P and PCIe PM observer patches. The WSA patch still failed after replaying the local WSA file changes. This is not evidence any change is redundant; do not apply with fuzz or enable QCE algorithms. The separate PLD `.ko` compiles, but the complete tested upstream trial also used PAS/DT changes and controlled its ADSP power notifications across sleep. The current channel is unbound; boot-time support and actual wake uplink remain unverified.

## First attended `deep` attempt (2026-11-28)

Read-only EFI preflight found only generations 9–16 (all short-release Next24, not cold-boot validated); the running accepted Gen 1 is marked selected/absent. The owner confirmed the validated r4 Live rescue USB was at hand and a power-cycle recovery was allowed. No boot entries, lid policy, sleep mode or drivers were changed.

The owner observed only a brief blank screen followed by the lock screen. Kernel monotonic log: `PM: suspend entry (deep)` at `68420.572011`, `PM: suspend exit` at `68423.179011` (~2.61 s for the entire kernel transaction). Counters changed `0/0 → 1/0`, boot ID unchanged; `pm_wakeup_irq` reported no data. This establishes that the kernel executed a `deep` cycle, not that the SoC stayed in low power for 15 s or that the wake source is known. It is not suspend acceptance.

The stock touch HID re-enumerated and `/dev/surface/denali/ipts` pointed to the new `hidraw7`, but `denali-iptsd.service` stopped after I/O error and stayed inactive even though the device returned. FullIO's existing keeper logged one new epoch with `0 dB`, GainStep 30, gain and unmute ACKs; protected speaker and MicArray nodes reappeared. No audible playback/duplex test or further suspend was run. The stock service was started once to recover touch; the owner chose not to pursue an IPTSD resume fix. The read-only snapshot now captures the BOOTTIME–MONOTONIC offset, per-source wake counters, and readable debugfs wake/residency tables. The new same-boot baseline shows only ~9.7 ms total BOOTTIME offset, consistent with a short transition rather than sustained sleep; a paired pre/post snapshot is needed to assign an interval to a particular trial. Surface logs: `/tmp/denali-todo2-deep-{before,after,kernel,request,preflight}.log`.

## Isolated QCE follow-up

The boot log names `1dfa000.crypto` as the consumer keeping both `interconnect-1` and `1700000.interconnect` in `sync_state() pending`. The actual kernel does not enable `CONFIG_CRYPTO_DEV_QCE`; this node has no driver or live consumers. `/soc@0/crypto@1d88000` is a different inline-crypto engine (ICE) and separately holds GCC; it is not part of this experiment. GMU also holds GCC/GPUCC and has HFI/OOB timeouts in this boot even though the Adreno component binds and loads firmware. An unbound GMU platform node alone does not identify the necessary fix, and disabling it is not a safe stand-in for debugging it.

Native `nix build --no-link .#denali-qce-disabled-dtb-candidate` passed. It is derived from the stock DTB (not the native-touch DTB); a sorted decompile diff found only `status = "disabled"` at `/soc@0/crypto@1dfa000`. SHA-256 `dd1f802ca4c2a735f65185f889cf35285e7ca3990f221bc0365a43a5dec82d3a`. No algorithms, ICE/GMU, speaker, touch, or Live configuration was changed. On a separate future boot, first compare the two ICC `state_synced` bits against stock before attempting a matched `s2idle` run; removing the QCE edge alone is not a promised residency improvement.

## What requires a local operator later

1. Compare the next ordinary lock's label with SAM `BAT1`. Test actual energy change over a longer stable battery interval separately; do not infer charge policy from a short unplug/replug.
2. Before any sleep attempt, have the owner at the power button with the current boot/recovery entry intact. Separate short explicit `deep` and `s2idle` tests and check the actual mode and wake logs. A failed resume can require power cycling, so do not run these while reboot is unavailable. Once short cycles are reliable, measure ≥2 h at midrange charge with matched peripherals/network, using `BAT1/energy_now` plus root-readable Qualcomm sleep residency. Read the counters; do not change the PM debug policy to obtain them.
3. Validate FullIO playback and simultaneous internal MicArray after waking before doing any WSA or ADSP A/B; service state alone does not prove this. Retain protection, 0 dB, HHKB, touchpad, OLED, NVMe, Wi-Fi and Bluetooth checks. Do not set auto-suspend before wake reliability, drain and rollback are all accepted.
